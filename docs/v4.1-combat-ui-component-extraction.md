# MVP-v4.1 規劃：Combat UI Component Extraction

日期：2026-05-11

## 目標

MVP-v4 已完成第一輪戰鬥 UI 視覺調整與 helper 分區，但主要畫面仍集中在 `scripts/Game.gd` 動態生成。MVP-v4.1 的目標是把已穩定的戰鬥 UI 區塊抽成可重用元件，降低後續新增 icon、角色立繪、卡牌圖片與更多戰鬥提示時的修改成本。

本階段重點是工程整理與可維護性，不重新設計畫面。

## 非目標

- 不重做整套戰鬥 UI 視覺。
- 不新增角色、卡牌、敵人、relic 或事件內容。
- 不導入正式人物圖、正式卡圖或正式 icon asset pipeline。
- 不把所有 `Game.gd` 畫面一次拆完；只處理戰鬥 UI 中最常變動、最需要測試保護的部分。
- 不改 CombatEngine 規則與卡牌平衡。

## 目前問題

- `Game.gd` 同時負責流程、狀態、戰鬥畫面、卡牌框架、手牌扇形排列、商店商品與 reward card 呈現。
- 卡牌框架在戰鬥、獎勵、商店中共用概念，但建立方式仍散在多個 helper。
- 手牌 hover 與扇形位置是高風險 UI 行為，後續改圖或改比例時容易回歸閃爍、跑版或文字裁切問題。
- 玩家 / 敵人狀態列已視覺穩定，適合先抽成獨立元件，之後再替換為 icon 呈現。

## 建議抽取順序

### 1. CombatCardView

用途：統一卡牌外觀與文字區塊。

建議路徑：

- `scripts/ui/CombatCardView.gd`

輸入資料：

- `card`：卡牌資料 dictionary。
- `mode`：`combat_hand`、`reward`、`shop`、`campfire`、`remove_card`。
- `badge_text`：左上角顯示內容，例如費用、價格、移除卡費用。
- `size`：實際卡牌尺寸。
- `show_description`：是否顯示效果說明。
- `click_callback`：點擊後回呼。

負責內容：

- 卡牌外框。
- 左上角 badge。
- 卡名。
- 圖片預留區。
- 類別文字。
- 效果說明。
- 卡牌類型顏色。

不得負責：

- 手牌扇形位置。
- hover 放大位置。
- 戰鬥規則。
- 商店扣款或獎勵邏輯。

驗收條件：

- 戰鬥手牌、戰鬥獎勵、商店卡牌、商店 relic / 移除卡服務都能使用同一套 card view 建立。
- 戰鬥獎勵卡牌不啟用 hover 放大。
- 商店左上角顯示金額，卡面下方顯示功能說明。
- 現有 `combat_ui_layout_tests.gd` 保持通過。

### 2. CombatHandView

用途：專門管理戰鬥手牌排列與 hover 行為。

建議路徑：

- `scripts/ui/CombatHandView.gd`

輸入資料：

- `hand_cards`：目前手牌資料。
- `screen_size`：目前 viewport 尺寸。
- `energy`：目前能量，可用於後續 disabled state。
- `play_card_callback`：點擊卡牌後呼叫。

負責內容：

- 手牌以畫面中央為核心排列。
- 中間較高、左右較低的底部扇形。
- 少量手牌仍往中央集中。
- hover 時卡牌轉正、放大、底部貼齊畫面下緣、置於最上層。
- hover 大卡用實際尺寸重排文字，不用 `scale` 整張縮放。

不得負責：

- 卡牌內部框架細節。
- 卡牌效果執行。
- 回合結束按鈕。

驗收條件：

- 1 到 5 張手牌都以中央為核心。
- hover 不閃爍。
- hover 後文字清楚，描述區盡可能完整呈現。
- hover 大卡可以蓋過角色與敵人。
- `combat_ui_layout_tests.gd` 覆蓋少量手牌置中、扇形、hover 置頂與底部貼齊。

### 3. ActorStatusView

用途：統一玩家與敵人的名稱、HP、格擋、能量 / 意圖 / 狀態文字呈現。

建議路徑：

- `scripts/ui/ActorStatusView.gd`

輸入資料：

- `actor_name`
- `hp`
- `max_hp`
- `block`
- `energy`
- `intent_text`
- `status_text`
- `passive_text`
- `side`：`player` 或 `enemy`

負責內容：

- 角色名稱。
- HP / 格擋 / 能量文字。
- 敵方意圖 icon placeholder 與文字 fallback。
- 角色下方狀態文字。
- 文字陰影或描邊。

不得負責：

- sprite 動畫。
- 敵人 AI。
- 狀態規則計算。

驗收條件：

- 玩家資訊不顯示抽牌 / 棄牌。
- HP / 格擋 / 能量不恢復深色底色。
- 敵方意圖不恢復深色底色。
- 文字在背景上仍清楚可讀。

## 暫緩抽取項目

以下項目可以等 V4.1 第一輪完成後再判斷是否拆出：

- `EnemyIntentView`：目前可先包含在 `ActorStatusView`，等 icon asset 正式化再獨立。
- `PassiveView`：目前文字量少，可先保留在 `ActorStatusView` 或 `Game.gd` helper。
- `RelicSummaryView`：目前只是一行文字，等 relic icon 化再抽。
- `DebugOverlayView`：debug 熱鍵說明仍可留在 `Game.gd`。
- `ShopGridView`：商店也使用 card view，但整個 shop layout 可等 Combat UI 抽取完成後再整理。

## 建議實作策略

1. 先建立 `scripts/ui/` 目錄與 `CombatCardView.gd`。
2. 把現有卡牌框架 helper 搬進 `CombatCardView`，讓 `Game.gd` 只傳入 card、mode、size 與 callback。
3. 跑 `combat_ui_layout_tests.gd`，確認 combat / reward / shop card 結構沒有退化。
4. 建立 `CombatHandView.gd`，先只接管 `_add_combat_hand_ui`、`_combat_hand_card_position`、hover 狀態。
5. 跑 UI layout 測試，特別驗證 1 到 5 張手牌置中與 hover 不閃爍。
6. 建立 `ActorStatusView.gd`，接管玩家與敵方文字欄位。
7. 最後整理 `Game.gd`，只留下流程控制、畫面切換與資料傳遞。

## 風險與注意事項

- Godot 動態 UI 與 scene/component 抽取之間需要取平衡。V4.1 建議先用 script component / factory 方式抽取，不急著全部改成 `.tscn`。
- hover 行為最容易回歸閃爍。抽取時要保留目前「原本位置命中、放大後置頂」的互動模型。
- 商店與 reward 雖然共用 card view，但不應繼承戰鬥手牌 hover 規則。
- 這次是整理既有 UI，不應順手修改卡牌數值、敵人數值或事件內容。
